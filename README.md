# ホットクック自作レシピ

ホットクックで作った自作レシピを Markdown で管理し、料理名や具材で探せる静的サイト。
リポジトリそのものがレシピの保管場所（バックエンド）になります。

> **使用機種**: ◯◯◯（自分のホットクックの機種名を記入）
>
> 自動メニュー番号は機種によって変わるため、このリポジトリの番号はこの機種が基準です。
> レシピ自体には機種を記録しません。

**公開先: https://thinkami.github.io/hotcook_recipe/**

`public/` を静的配信すれば動きます。手元で見るには、たとえば次のようにします。

```bash
npm run build && python3 -m http.server 8765 --directory public
```

## 公開

サイトは [GitHub Pages](https://thinkami.github.io/hotcook_recipe/) で公開しています。

| 何をしたとき | 何が起きるか |
|---|---|
| プルリクエストを出す | ビルド・テスト・静的検査・整形の確認だけが走る。公開はされない |
| `main` に取り込む・直接 push する | 同じ検証が走り、成功すれば公開される |
| Actions から手動実行する | 同じ検証が走り、成功すれば公開される |

検証が1つでも失敗すると公開の手順に進みません。そのとき公開中のサイトは、直前に成功した
内容のまま配信され続けます。壊れたレシピを取り込んでも公開サイトは壊れません。

ブランチ保護はかけていません。検証が赤くてもマージはできます（不備に早く気づくための
情報であって、関門ではありません）。

公開経路では **読みの対応表を作り直しません**。読みの取得は macOS を要するため、
Linux で動く公開経路では実行できないからです。対応表はコミット済みのものがそのまま使われます。
更新したいときは、手元で `npm run yomi:update` を実行してコミットしてください
（詳しくは「読みの対応表」の節）。

### 公開のための設定（一度だけ）

リポジトリの **Settings → Pages → Build and deployment → Source** を **GitHub Actions** に
設定してください。既定の「Deploy from a branch」のままだと、公開のワークフローが失敗します。

## セットアップ

Node.js の版は [.node-version](.node-version) に固定しています（mise を使う場合は [mise.toml](mise.toml) の設定で
このファイルを読みます。使わない場合も同じ版を用意してください）。

```bash
npm ci
```

## レシピを追加する

`recipes/` に `<ローマ字スラッグ>.md` を作ります（例: `mushi-broccoli.md`）。
**ファイル名がそのままレシピの ID** になり、あとで URL に載ります。小文字・ハイフン区切りで付けてください。

```markdown
---
title: 蒸しブロッコリー      # 必須・料理名
ingredients:                 # 必須・1件以上。量と単位は分けず1行ずつ
  - ブロッコリー 1つ
manual_note: 蒸し野菜 5分    # 任意・手動設定
---

本文に手順やメモを Markdown で書く
```

- `auto_key` / `menu_no` / `manual_note` は任意で、**組み合わせは自由**です
  （自動調理キーと手動設定の両方、番号だけ、どれも書かない、いずれも可）
- `menu_no` は **必ず引用符で囲みます**（例: `menu_no: "048"`）。`menu_no: 048` と書くと数値として読まれ、先頭のゼロが失われます
- 上の5つ以外のキーを書いても失敗はしませんが、検索用データには入りません
- `title` が無い／`ingredients` が空だと、ビルドが**わざと失敗**して気づけるようにしています

追加したら、ビルドが通ることを確認します。

```bash
npm run build
```

不備があるとファイル名と理由が一覧で出ます。1件目で止まらず全部まとめて出るので、
一度に直せます。不備があるあいだは検索用データを書き出さないため、前回の成功版は壊れません。

## コマンド

| コマンド | 内容 |
|---|---|
| `npm run build` | `recipes/*.md` を検証して `public/recipes.json` を生成する |
| `npm run yomi:update` | 読みの対応表（`data/yomi.generated.json`）を作り直す（**macOS のみ**） |
| `npm test` | テストを1回実行する |
| `npm run test:watch` | テストを監視実行する |
| `npm run test:coverage` | カバレッジ付きでテストを実行する |
| `npm run lint` | oxlint で検査する |
| `npm run lint:fix` | oxlint で自動修正する |
| `npm run format` | oxfmt で整形する |
| `npm run format:check` | 整形済みかを確認する |

`public/recipes.json` はビルド生成物なのでコミットしません（`.gitignore` 済み）。
一方、`data/` の読みの対応表は**コミットします**（理由は次節）。

## 読みの対応表

材料は `味噌 大さじ2` `大根 1/3本` のように漢字で書きますが、探すときは「みそ」
「だいこん」とかなで打ちます。この差は文字列としては埋まらないので、語と読みの
対応表を持ち、ビルド時に検索用データへ焼き込んでいます。

```
data/yomi.generated.json   自動生成。npm run yomi:update でまるごと作り直す。手で編集しない
data/yomi.overrides.json   誤読を手で直す場所。生成処理は読み書きしない
```

### 育て方

レシピを追加したら、対応表を作り直してからビルドします。

```bash
npm run yomi:update
npm run build
```

**生成された差分は必ず目で見てください。** 読みの誤り（例: `葱` が `き` になる）は
かなとして正しい形で出るため、機械には判定できません。差分レビューだけが気づく手段です。

誤りを見つけたら `data/yomi.overrides.json` に書きます。訂正は再生成では消えません。

```json
{
  "葱": "ねぎ",
  "米": "こめ"
}
```

### ビルドが出す警告

失敗はせず、直すと消えます。

| 警告 | 意味 |
|---|---|
| 読みを取得できていません | その語がかなで引けない。訂正に読みを書く |
| 読みに漢字が残っています | 対応表に語が足りない。`npm run yomi:update` を実行するか訂正を書く |
| どのレシピにも現れない語の訂正です | レシピから消えた語。訂正を削除できる |
| 自動生成された読みと同じ値です | エンジン側が直った。訂正を削除できる |

読みの取得には macOS の日本語エンジンを使うため、**生成できるのは macOS だけ**です。
ただし対応表はコミットしてあるので、ビルド・テスト・公開はどの環境でも動きます。

## 構成

```
recipes/     著者が編集する1レシピ1ファイル
public/      公開される静的サイト（検索画面と、ビルドで生成される recipes.json）
data/        読みの対応表（入力でも公開物でもない中間物。コミットする）
scripts/     ビルド（frontmatter の切り出し・検索用データの生成・読みの取得）
tests/       テストとフィクスチャ
openspec/    仕様と設計の記録（spec 駆動で開発しています）
.github/     検証と公開のワークフロー
```

なぜその作りにしたかは `openspec/` の各 change に記録しています。
