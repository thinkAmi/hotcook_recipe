## Why

Phase 1 でレシピの記述形式と検索用データの生成までは整った。しかしレシピを探す画面がまだ無く、「今日何を作ろう」と思ったときにリポジトリの Markdown を直接開くしかない。データはあるのに目的を果たせていない状態なので、探して読める画面をこの change で用意する。

あわせて、実際に探そうとすると表記の壁がある。材料は `味噌 大さじ2` `大根 1/3本` のように漢字で書かれる一方、探すときは「みそ」「だいこん」とかなで打つため、文字列としては一致しない。「読み」を導入してこの壁を越える。

## What Changes

- 1つの入力にすべてを寄せた検索画面を追加する。スペース区切りは AND、入力前は全件を料理名順に表示する
- レシピの詳細（料理名・調理方法・材料・手順）をダイアログで表示する。URL のハッシュを開閉の唯一の起点とし、スマホの「戻る」で閉じられるようにする
- 検索語を URL に反映し、再読み込みやモバイルのタブ復元で検索状態が戻るようにする
- 「読み」を導入する。料理名・材料・自動調理キー・手動設定に対応する読みを検索用データに持たせ、かなで打っても漢字表記のレシピが引けるようにする
- 読みの対応表を、自動生成される部分と著者が訂正する部分に分けて保持する。著者の訂正は再生成で失われない。読みを取得できなかった語はビルドが警告する
- ブラウザで動く第三者コードは1行も増やさない。検索は表記のゆれを吸収する正規化と部分一致で行う
- 用語集に「読み」を追加する（`openspec/config.yaml` の context）

## Non-goals

- GitHub Pages への公開・CI（次の change）
- 検索語のハイライト。検索結果は料理名だけを出すため、短い料理名を強調する情報価値が薄い。必要と感じたら後から足す
- 入力側に漢字を打って、かな・カナ表記のレシピを引くこと（例: 「鯖」で `サバ` を引く）。読みはデータ側の一方向にしか効かない。かなで打てば引けるので、当面はそれを回避手段とする
- AND 以外の演算子（OR・除外・完全一致）。小さく始め、必要になってから足す
- 一致度順の並び替え、材料や調理方法ごとの絞り込み UI
- 汎用の日本語辞書をリポジトリに同梱すること。読みはレシピに現れる語の分だけ持つ
- 意味検索・AI 連携（構造化データの層分離を壊さないことだけ守る）
- レシピの記述形式の変更。frontmatter の項目は Phase 1 のまま増やさない

## Capabilities

### New Capabilities
- `recipe-yomi`: 語と読みの対応表の扱い。自動生成される部分と著者が訂正する部分の分離、再生成が訂正を壊さないこと、読みを取得できなかった語の扱い、掃除を促す警告
- `recipe-search`: 1つの入力での検索の振る舞い。表記のゆれの吸収、AND の意味、検索対象、並び、初期表示、日本語入力中の扱い、検索語の URL 反映、0件時と読み込み失敗時の表示
- `recipe-detail`: レシピ詳細の表示。表示する項目と順序、調理方法の出し方、URL ハッシュを起点とした開閉と履歴の扱い

### Modified Capabilities
- `search-index`: レシピオブジェクトが読みを持つ。料理名・材料・自動調理キー・手動設定に対応する読みのキーが加わり、8キーから12キーになる

## Impact

- 新規: 公開ディレクトリの HTML・CSS・JS（検索画面と詳細表示）、読みの対応表を置くディレクトリ、読み表を生成するスクリプト、それらのテスト
- 変更: ビルドが検索用データに読みを焼き込む。README にコマンドと読み表の育て方を追記
- 用語: `openspec/config.yaml` の用語集に「読み」を追加する
- 依存: ブラウザで動く第三者コードは増やさない。プロダクション依存（ビルド時）も増やさない。読み表の生成は追加の依存を持たない手段で行う（詳細は design）
- 生成物: 読みの対応表はリポジトリにコミットする。検索インデックスはこれまでどおりコミットしない。生成物のコミット方針は Phase 1 の決定（D-09）の適用範囲を design で明示し直す
- 後続 change への契約: 公開は公開ディレクトリ配下をそのまま配信すれば足りる。読み表の生成は公開経路では実行しない
