## Context

Phase 1（change `recipe-data`）で、レシピの記述形式と検索インデックス（`public/recipes.json`）の生成までができている。この change では、そのインデックスだけを入力として検索画面と詳細表示を作る。レシピの Markdown をブラウザから直接読む設計にはしない。

設計を始める前に実データで確かめたところ、素朴なかな正規化だけでは足りないことが分かった。材料は `味噌 大さじ2` `大根 1/3本` のように漢字で書かれる一方、探すときは「みそ」「だいこん」とかなで打つ。この差は正規化でも編集距離でも埋まらない。そこで「読み」という概念を持ち込む。

制約（config.yaml の常設制約より）: プロダクションコードは可能な限り標準 API のみ／フロントは HTML+CSS+JS でフレームワーク・バンドラを使わない／ブラウザで動く第三者コードは最小限、使うなら vendoring＋SRI／重い処理はビルド時に寄せる／不備は fail fast／構造化データと層分離を壊さない／開発ツールは oxlint・oxfmt・vitest・fast-check。

用語: この change で「読み」を導入する。`openspec/config.yaml` の用語集にも追加する。

## Goals / Non-Goals

**Goals:**
- 1つの入力に打つだけで、料理名でも材料でもレシピにたどり着ける
- 漢字で書かれた材料を、かなで打って引ける
- ブラウザで動く第三者コードを1行も増やさない
- 読みの誤りに人が気づけて、直した内容が失われない
- スマホで、調理中に片手で使える

**Non-Goals:**
- GitHub Pages への公開・CI（次の change）
- 検索語のハイライト（D-25 で不採用とした）
- 入力側の漢字をかなに読み替えること
- AND 以外の演算子、一致度順の並び替え、絞り込み UI
- 汎用の日本語辞書の同梱

## Decisions

### データ層（読みと検索インデックス）

#### D-13 レシピ側の漢字表記は「読み」で引けるようにする
- **背景**: 実データで確かめると、`味噌`・`大根`・`豚バラ肉` は漢字で書かれる一方、探すときは「みそ」「だいこん」「ぶたばら」とかなで打つ。文字列としては一致せず、かな正規化（カタカナ→ひらがな・全角半角・大小文字）でも届かない。表記そのものが違うため。
- **検討した選択肢**:
  - 何もせず、かな正規化だけで済ませる → 実装ゼロだが「みそ」で `味噌` が引けない。主要な材料の多くが漢字なので実用に届かない
  - あいまい検索（Fuse.js など）を入れる → Bitap は編集距離ベースで、`さば`↔`サバ` すら別文字列として扱う。日本語で痛い揺れには無力で、解決するのはタイポ吸収だけ。第三者コードと SRI 運用のコストに見合わない
  - レシピの `id`（ローマ字スラッグ）を検索対象にし、入力をローマ字化して照合 → 追加データがゼロで料理名は救えるが、材料の読みは `id` に無い。かな→ローマ字の変換表を自前で持つ必要もある
  - frontmatter に検索用の語（`keywords`）を著者が書く → 確実だがレシピごとに書く手間が増え、語彙がレシピ間で共有されない
  - **語と読みの対応表を持ち、ビルド時に読みを焼き込む（採用）** → 語彙がレシピ横断で共有される。ブラウザには第三者コードが増えない。「重い処理はビルド時に寄せる」に忠実
- **帰結**: 検索インデックスに読みのキーが加わる（D-18）。対応表という新しいアーティファクトが生まれ、その運用を capability `recipe-yomi` として定める。`id` は変換なしでそのまま検索対象に含める（ローマ字で打った場合に効く。追加コストがゼロのため）。
- **見直し条件**: 入力側の漢字（「鯖」で `サバ` を引く）が実際に苛立つほど起きたら、対応表をブラウザにも配って入力にも同じ変換をかける（非破壊で足せる）。

#### D-14 読みは macOS 組み込みの日本語エンジンで取得し、退路として純 JS の形態素解析器を残す
- **背景**: 漢字→読みを返せるのは、読み付き辞書を持った形態素解析器だけ。ただし辞書は数MB〜数十MB あり、依存として重い。
- **検討した選択肢**（いずれもビルド工程を持たず導入できるものに絞って実測した）:
  - `kuromoji` 0.1.2（純JS・IPADIC 同梱、41.3MB、依存に古い `zlibjs`）→ 導入は容易だが更新が長く止まっている
  - `@sglkc/kuromoji` 1.1.0（同フォーク、18.3MB、`fflate` に更新済）→ 上より健全。**退路として採用**
  - `lindera-wasm` 2.1.0（1.9MB＋辞書別、保守は活発）→ cargo 不要で入るが、辞書調達の手間が残る
  - Janome 0.5.0（純Python 18.7MB、`uvx` で即実行）／fugashi＋unidic-lite（0.6＋45.1MB、読みの精度は最高クラス）／sudachipy＋core辞書（1.5＋68.9MB）→ いずれも動くが、npm の lockfile の外に依存が出る
  - MeCab → 未導入かつ環境依存が強く、開発機を選ぶ
  - **macOS 組み込みの日本語エンジン（採用）** → 追加インストールも辞書もゼロ。実測で `大蒜→にんにく` `南瓜→かぼちゃ` `味醂→みりん` `牛蒡→ごぼう` `舞茸→まいたけ` `青梗菜→ちんげんさい` `出汁→だし` まで正しく返し、料理語彙のカバレッジが最良クラスだった。何より**著者が日本語を打つときの変換エンジンと同一**なので、「自分が打つ読み」と構造的に一致する
- **帰結**: 読みの取得は macOS 上でのみ行う。生成物（対応表）はコミットするので、ビルド・CI・ブラウザは OS に依存しない（D-16）。実測で見つかった2つの罠に対処する必要がある。
  - ローマ字で連結してから一括でかな変換すると壊れる（`mirin`+`oosaji` → 「みりのおさじ」）。**トークンごとにかな化してから連結する**
  - 空白を含む文字列を渡すと中国語（ピンイン）と誤判定される（`生姜 1片` → 「しぇえんぐじああんぐ…」）。**空白で区切ってから語ごとに渡す**

  誤読は残る（実測で `葱→き`、`米→べい`）。これは自動検出できない（かなとして妥当な形で出るため）ので、対応表を差分レビューして人が直す前提にする（D-15）。
- **見直し条件**: macOS 以外で読みを生成する必要が出たとき。`@sglkc/kuromoji` を devDependency に足せば OS 非依存にできる。**対応表の形は変わらない**ので完全に非破壊で切り替えられる。

#### D-15 対応表は「自動で生成される部分」と「著者が訂正する部分」を別ファイルに分ける
- **背景**: 対応表は生成物でありながら手で直す対象でもある。誤読は機械に検出できないため、手修正が再生成で潰れると、誤読が復活したことにすら気づけない。
- **検討した選択肢**:
  - 1ファイルで追記のみ（表に無い語だけ足す）→ 実装は最小で手修正も守られるが、どの値が生成でどの値が人の判断か区別できない。レシピから消えた語がゴミとして残り続ける
  - 1ファイルで生成値と訂正値を併記（`{auto, fixed}`）→ 出自は明示されるが表が冗長になり、「触っていい場所」がファイル内の位置でしか区別されない
  - **2ファイルに分ける（採用）** → `data/yomi.generated.json`（自動生成・まるごと書き直す・手で触らない）と `data/yomi.overrides.json`（人だけが書く）。**触っていいファイルがファイル境界で物理的に分かれる**ので事故が構造的に起きない。生成側をまるごと書き直せるのでゴミが溜まらない。差分レビューも「レシピかエンジンの変化」と「人の判断」に自然に割れる
- **帰結**: ビルドは `{ ...generated, ...overrides }` の順にマージして引く。読みを取得できなかった語は生成側に `null` で残す。ビルドは3種の警告を出す——(1) `null` のまま訂正も無い語、(2) レシピから消えた語の訂正、(3) 生成値と同じ値になった訂正。いずれも警告であってビルドは失敗させない（新しい食材を書くたびに止まるのを避けるため）。訂正ファイルは macOS でなくても書けるので、別 OS でも運用を続けられる。ディレクトリ配置に `data/`（入力でも公開物でもない中間物の置き場）を新設する（D-11 の拡張）。
- **見直し条件**: 訂正が数百件規模になり、生成側との突き合わせが人手に負えなくなったとき。

#### D-16 対応表はコミットする（D-09 の適用範囲を明示し直す）
- **背景**: D-09 は「ビルド生成物はコミットせず、手元と CI で再生成する」と決めている。対応表は生成物なので、素直に読むとコミット禁止になる。
- **検討した選択肢**:
  - D-09 をそのまま適用してコミットしない → CI（Linux）で再生成できないため、そもそもビルドが通らない。誤読を差分レビューする手段も失われる
  - **D-09 の適用範囲を明示し、対応表はコミットする（採用）** → 区別の線は「**再生成に特定環境を要する**か、**差分が人のレビュー対象になる**もの」。対応表は両方に当てはまり、`recipes.json` はどちらにも当てはまらない
- **帰結**: `data/yomi.generated.json` と `data/yomi.overrides.json` をコミットする。`public/recipes.json` は引き続きコミットしない。生成物のコミット可否は今後もこの線で判断する。

  **公開経路（CI）では対応表の生成を実行しない**（次の change への申し送り）。Linux では読みを取得できないので実行すれば失敗する（D-14）。CI が行うのはビルドだけで足り、対応表はコミット済みのものをそのまま使う。
- **見直し条件**: 読みがどの環境でも再生成できるようになり、差分レビューが不要になったとき。

#### D-17 対応表は語単位で持ち、参照は最長一致で行う
- **背景**: 対応表を語単位にすると、生成時と参照時で語の切れ目がズレると引けなくなる。実測でも `豚バラ肉` は `豚` と `バラ肉` に分かれた。標準の `Intl.Segmenter` と形態素解析器の分割は一致しないため、分割器を2つ持つと必ずズレる。
- **検討した選択肢**:
  - フィールド単位の表（`サバの味噌煮 → さばのみそに`）→ 引くのは自明だが表が肥大し、同じ語が何度も登録される。訂正もレシピごとに繰り返しになる
  - 語単位＋参照時にも分割器を使う → 分割の一致を保証できず、ズレたら静かに引けなくなる
  - **語単位＋最長一致（採用）** → 表のキーを長い順に並べ、文字列の先頭から最長一致で置換していく。**分割器を持たずに済み、生成側の切り方に一切依存しない**
- **帰結**: 参照側は数十行で書ける純関数になり、テストしやすい。生成側は、**空白で区切った断片そのものと、その中の語（トークン）の両方**を表に積む。数字・記号・ラテン文字は表に入れない（`200g → 200ぐ` のようなノイズを避ける）。表に無い文字はそのまま残る。

  断片も積むのは、実装中に実データで踏んだ取り違えを塞ぐため。**同じ文字列が文脈によって違う切られ方をするので、片方の切り方が表に入るともう片方を潰す。**

  ```
  料理名「豚バラ大根」  → 豚バラ / 大根   と切れる → 表に「豚バラ」が入る
  材料「豚バラ肉 200g」 → 豚 / バラ肉     と切れる → 表に「豚」「バラ肉」が入る
                                                     「肉」単体は表に入らない

  最長一致で「豚バラ肉」を引くと「豚バラ」が勝ち、残った「肉」は引けずに
  「ぶたばら肉」になる（実測）
  ```

  断片「豚バラ肉 → ぶたばらにく」を積めば最長一致でこれが勝つので、**レシピに実際に現れる文字列は必ず正しく引ける**。語単位のエントリも残すので、語彙がレシピ横断で共有される利点は失われない。表は実測で 25語 → 35語程度に増える。

  「分割器を持たないので生成側の切り方に依存しない」は参照側については正しいが、**表の中身は生成側の切り方を引きずる**。この見落としが上の取り違えを生んだ。
- **見直し条件**: 表が数千語規模になり、最長一致の走査が体感で重くなったとき。

#### D-18 読みはフィールドごとに併記し、短い4フィールドにだけ持たせる
- **背景**: 読みを検索インデックスにどう載せるかで、下流の契約の形が決まる。実測では `title`＋`ingredients`＋`auto_key`＋`manual_note` が JSON 全体の 14.4%、`body` だけで 32.2% を占めた。読みは元表記より長くなる（漢字1文字がかな2〜4文字）。
- **検討した選択肢**:
  - 読みを1本の検索用テキストに集約（`search_yomi`）→ キーが1つで済むが、**検索実装の都合がデータ層の契約に染み出す**。将来 MCP 公開や意味検索を載せたとき、消費者にとって意味のないキーが契約として残る
  - 表記と読みをまとめて1本に集約（`search_text`）→ ブラウザのコードは最小になるが、元表記が JSON 内に二重に載る。上と同じ層分離の問題も抱える
  - **フィールドごとに併記（採用）** → `title_yomi` は「料理名の読み」というレシピの属性であり、将来どの消費者にも意味がある。8キー → 12キー。ブラウザ側の連結は数行で済む
  - 読みを `body` にも持たせる → JSON が約 +65% になるうえ、本文由来の語で対応表が膨らみ、誤読の差分レビューの負担が増える。手順を読みで引く需要は薄い。**不採用**（短い4フィールドのみなら約 +20% に収まる）
- **帰結**: 読みのキーは常に存在し常に文字列（元表記と同じ値になる場合も省略しない。D-06 の踏襲）。読みを取得できなかった語はその語だけ元表記のまま残す（フィールド全体は空にしない）。`menu_no` は数字なので読みを持たない。`body` は元表記のまま検索対象には残す（「圧力」と漢字で打てば当たる）。
- **見直し条件**: 手順を読みで引きたくなったとき。`body_yomi` を足せばよく、既存の契約は壊れない。

#### D-28 読みに漢字が残っていたらビルドが警告する
（実装中に D-17 の取り違えを踏んで足した決定。番号は通しのため、この節の末尾に置く）

- **背景**: D-15 で定めた3種の警告は、いずれも対応表そのものを見て判定する。しかし D-17 の帰結に書いた取り違え（`豚バラ肉 → ぶたばら肉`）は、表の中身としてはどのエントリも正常なので3種のどれにも掛からない。読みが不完全なまま静かに検索が当たらなくなる、いちばん厄介な壊れ方が素通りする。
- **検討した選択肢**:
  - 警告を足さない → D-17 の対策（断片も積む）で今回の原因は塞げるが、塞ぎ漏れたときに気づく手段が無いままになる。誤読と違い、この壊れ方は**機械で判定できる**のに検出しないのはもったいない
  - ビルドを失敗させる → 気づけはするが、新しい食材を1つ書くたびに公開が止まる。D-15 で「警告であって失敗させない」と決めた理由がそのまま当てはまる
  - **組み立て後の読みに漢字が残っていたら警告する（採用）** → 判定は `normalizeYomi` が単語に対して既に行っているものと同じ規則で、適用範囲をフィールドに広げるだけ。実装は数行
- **帰結**: ビルドの警告は4種になる。1〜3 は対応表を見て判定し、4 は組み立てた結果を見て判定する。実測ではこの警告が `豚バラ肉 200g → ぶたばら肉 200g` をただ1件として正しく拾った。誤読（`葱→き`）は依然として検出できない——かなとして妥当な形で出るため——ので、対応表の差分レビューが要ることは変わらない。
- **見直し条件**: 漢字を含む固有名詞をあえて読みなしで残したくなったとき。そのときは訂正で読みを明示するか、警告の除外を設ける。

### 検索

#### D-19 検索は自前の正規化＋部分一致で行い、ブラウザで動く第三者コードを増やさない
- **背景**: 「Google 検索のように1つの入力で探す」ために何が要るかを分解すると、(1) 全項目を横断する、(2) 表記の揺れを吸収する、(3) タイポを吸収する、(4) 論理演算、になる。日本語で効くのは (1)(2) で、(3) の価値は薄い。
- **検討した選択肢**:
  - Fuse.js → 買えるのは (3) だけ。(2) には無力（D-13 参照）。加えて vendoring＋SRI＋台帳の運用コストが乗る
  - MiniSearch / FlexSearch / lunr.ja / Pagefind / Orama などの検索エンジン系 → トークナイズ（語境界）は解くが読みは解かない。そして今回は部分一致なので語境界を知る必要がそもそも無い
  - **標準 API による正規化＋`includes` の総当たり（採用）** → 第三者コードがゼロ。レシピ数十件 × 数フィールドの走査はブラウザにとって計測に値しない量
- **帰結**: `vendor/` も SRI も台帳も不要になり、proposal 段階で想定していた第三者コード用の capability を立てずに済む。検索ロジックは DOM に依存しない純関数として切り出す（D-27）。
- **見直し条件**: レシピが数百件を超え、総当たりが体感で重くなったとき。そのときも `id` の安定性（D-05）があるので、別実装への差し替えは局所で済む。

#### D-20 正規化はブラウザ起動時に1回行う（ビルド時に寄せない）
- **背景**: 常設制約は「重い処理はビルド時に寄せる」だが、正規化（NFKC・カタカナ→ひらがな・小文字化）をビルド時に行うと、正規化済みテキストを検索インデックスに持たせることになり、`search-index` の契約が検索実装に引きずられる。
- **検討した選択肢**:
  - ビルド時に正規化済みテキストを持つ → 制約には忠実だが、JSON が膨らみ、正規化ルールを変えるたびに再ビルドが要る。データ層の契約に検索の都合が入る
  - 検索のたびに毎回正規化する → 実装は単純だが打鍵ごとに全件を正規化する
  - **起動時に1回だけ正規化してメモリに持つ（採用）** → 実測規模（数十件・数KB）では体感ゼロ。**正規化ルールの変更が UI 側だけで完結する**
- **帰結**: 常設制約を一部覆す決定として明示する。分担は「連結と読みはビルド、正規化はブラウザ」。読みだけがビルド時にしか作れないので JSON が運び、正規化はルールが変わりうるので UI 側に置く、という線引きになる。
- **見直し条件**: レシピが数百件規模になり、起動時の正規化が体感できるようになったとき。

#### D-21 演算子は空白区切りの AND だけにする
- **背景**: 1つの入力にすべてを寄せる方針では論理演算を記号で表すことになるが、主な利用環境はスマホで、フリック入力で `|` や `!` を出すのは手間が大きい。
- **検討した選択肢**:
  - OR・除外・完全一致まで用意する → 表現力は上がるが、覚える記号が増えて「1つの入力に寄せる」利点を削る。数十件規模なら除外は目で飛ばす方が速い
  - 完全一致（`=`）を用意する → 自前の部分一致では既定が既に厳密一致なので、意味を持たない
  - **空白区切りの AND だけ（採用）** → 覚えることがゼロ。あとから演算子を足しても `さば みそ` の意味は変わらないので、**非破壊で拡張できる**
- **帰結**: 空白以外の記号は語の一部として扱う。必要になったら後から足す。
- **見直し条件**: レシピが増えて AND だけでは絞りきれなくなったとき。まず除外（`!`）から検討する。

#### D-22 検索結果の並びは料理名順のままにする
- **背景**: 絞り込んだ結果をどう並べるかは、一致度順と入力順（＝料理名順）の二択になる。
- **検討した選択肢**:
  - 一致度スコア順 → 「らしい」が、部分一致では当たり外れの二値しかなくスコア設計を新たに作ることになる。どのフィールドの一致を重く見るかという恣意的な重み付けも必要
  - **料理名順のまま（採用）** → スコア設計が不要。**並びが常に同じ**なので、同じ検索を繰り返したときに目が慣れる
- **帰結**: D-07（料理名の日本語ロケール昇順）がそのまま表示順になり、ビルド側の並びを緩める必要が無くなる。
- **見直し条件**: レシピが増えて、一致したレシピが1画面に収まらないことが常態化したとき。

#### D-23 検索語はクエリパラメータに置き、履歴は増やさない
- **背景**: 詳細の開閉は URL の `#` で表す（D-26）ため、`#` 付きの URL で再読み込みすると検索語だけが失われる。スマホではバックグラウンドのタブが破棄されて戻ったときに再読み込みされることが多く、まさに調理中の使い方でこれが起きる。
- **検討した選択肢**:
  - 検索語を保持しない → 実装ゼロだが、タブ復元のたびに打ち直すことになる
  - `sessionStorage` に保持する → URL を汚さず履歴も触らないが、**状態の置き場所が URL と別系統に二重化する**。「状態は URL に置く」という詳細表示側の方針と揃わない
  - **クエリパラメータに置く（採用）** → 状態の置き場所が URL に統一される。実装は実質3行
- **帰結**: 次の3つをルールとして守る。破ると壊れる。
  1. 書き込みは履歴を置き換える方式だけを使い、履歴を積む方式は使わない（打鍵のたびに履歴が積まれると、スマホの「戻る」がダイアログを閉じる操作として機能しなくなる）
  2. 読み取りは画面を開いたときだけ行い、「戻る／進む」では読み直さない（進んだ先に古い検索語が残っていると、入力欄が勝手に書き換わる）
  3. 書き換えるときは `#` に続く部分を保持する（落とすとダイアログが閉じる）

  加えて、外部リンクをたどったときに検索語がリファラとして外部へ出るため、リファラを送らない設定をページに置く。D-24（日本語入力の確定後にのみ検索する）と組み合わさるので、未確定の文字が URL に載ることはない。
- **見直し条件**: 検索語以外にも URL に載せたい状態が増えたとき。

#### D-24 日本語入力の変換が確定するまで検索結果を更新しない
- **背景**: 打鍵のたびに検索すると、日本語入力では変換確定前の未確定文字でも検索が走る。「さ」→「さb」→「さば」と打つ過程で結果が入れ替わり続け、探しているあいだ画面が落ち着かない。変換候補を選ぶ前の中途半端な文字列で一時的に0件になることもある。
- **検討した選択肢**:
  - 打鍵のたびに検索する → 実装は最も単純だが、日本語入力では上記のちらつきが常に起きる
  - 一定時間入力が止まってから検索する（デバウンス）→ ちらつきは減るが、変換の途中でも時間が経てば走るため根治しない。待ち時間の調整という新しい恣意も生む
  - Enter などで明示的に検索を実行する → ちらつきは無いが、1つの入力で素早く絞り込む体験から遠のく
  - **変換が確定したときにだけ検索する（採用）** → 日本語入力では変換確定こそが意味のある区切りそのもの。英数字だけを打つ場合は従来どおり打鍵ごとに走る
- **帰結**: 未確定の文字が検索語として扱われることが無くなり、URL にも載らない（D-23）。変換に関わるイベントの挙動は端末と IME で差があるため、実機で確認したうえで調整する。
- **見直し条件**: 実機で変換確定を安定して検出できないと分かったとき。そのときはデバウンスとの併用を検討する。

#### D-25 検索語のハイライトは作らない
- **背景**: 当初は料理名と材料をハイライトする想定だったが、検索結果に出すのを料理名だけに絞った（一覧性を優先。探している段階では料理名で足りる）ことで前提が変わった。
- **検討した選択肢**:
  - 一覧と詳細の両方でハイライトする → 一覧は料理名だけなので短く、一致していれば一目で分かる。ハイライトの情報価値がほぼ無い
  - 詳細の材料だけハイライトする → 「なぜこれが出たか」を示せるが、**読みで一致した場合はハイライトできない**（読みと元表記の文字単位の対応が無いため）。`みそ` で `味噌` に当たった、まさに一番分かりにくいケースで機能しない。逆に機能するのは自分で漢字を打った場合で、そのときは説明が要らない
  - 読みの置換記録を残して元表記の位置を復元する → 実装できるが、得られる価値に対して複雑さが釣り合わない
  - **作らない（採用）** → 要件が1つ減り、`body_html` の信頼境界（D-03）に触れる話も完全に消える
- **帰結**: 検索結果は料理名だけを表示する。必要と感じたら後から足せる（既存の契約を何も変えずに追加できる）。
- **見直し条件**: 実際に使って「なぜこれが出たのか」が分からず困る場面が続いたとき。まず詳細の材料への直接一致だけを対象に検討する。

### 詳細表示

#### D-26 詳細はダイアログで表示し、URL の `#` を開閉の唯一の起点にする
- **背景**: スマホで詳細を開いたまま戻るジェスチャをしたときにサイトごと離脱するのは避けたい。一方、ダイアログの開閉状態と履歴を別々に管理すると、両者がずれるバグが起きやすい。
- **検討した選択肢**:
  - 画面遷移にする（一覧ページと詳細ページを分ける）→ 静的サイトではページを増やすかルーティングを自作することになり、検索状態も失われる
  - ダイアログを持つが URL は変えない → 実装は単純だが、戻るジェスチャでサイトを離脱してしまう
  - ダイアログの開閉を独自の状態として持ち、URL と双方向に同期する → 同期のずれが構造的に起きうる
  - **`#` に置いたレシピの ID を唯一の起点にする（採用）** → 開くのも閉じるのも `#` を変えるだけになり、履歴との同期が一方向になってずれようがない。フォーカス管理は標準のモーダル表示に任せる
- **帰結**: 閉じる操作は履歴を1つ戻す方式に寄せる。ただしレシピの ID を含む URL で直接開いた場合は戻り先が無いので、そのときは履歴を置き換えて `#` を取り除く。直リンクやブックマークは想定しないが、再読み込み時に破綻しないための退路として必要になる。どのレシピにも一致しない ID は開かず一覧を表示する。
- **見直し条件**: 詳細に一覧へ戻る以外の遷移（次のレシピへ、など）が必要になったとき。

### 横断

#### D-27 テストは、検索ロジックと対応表の純粋な部分を切り出して行う
- **背景**: Phase 1 は D-10 で「純関数として切り出して直接テストする」方針を採り、frontmatter スプリッタでそれが機能した。Phase 2 には新しい事情が2つある——ブラウザで動くコードが増えること、対応表の生成が macOS でしか動かず CI でテストできないこと。
- **検討した選択肢**:
  - jsdom / happy-dom を devDependency に足して DOM ごとテストする → 画面の組み立てまで検証できるが、開発時依存が増え、テストが DOM の再現度に左右される
  - ブラウザのコードをテストしない → D-19 で「第三者コードを使わず自前で書く」と決めた以上、正しさを自分で担保する必要がある。空手形になる
  - **DOM に依存しない純関数として切り出してテストする（採用）** → 正規化・語の分割・一致判定・並び替えはすべて文字列とデータの関数として書ける。対応表も、最長一致の置換・生成側と訂正側のマージ・3種の警告判定は純粋な部分として切り出せる。**macOS でしか動かないのは読みの取得だけ**なので、そこだけを差し替え可能な境界にすれば残りは CI でテストできる
- **帰結**: プロパティで固定する性質は次の3つ。
  - (a) 正規化の冪等性: 任意の文字列に対し、正規化を2回かけた結果は1回かけた結果と等しい
  - (b) マージ規則: 訂正のある語では、生成側の値によらず必ず訂正の値が採られる
  - (c) 再生成の非破壊性: 任意の訂正に対し、生成側をどう作り直しても訂正の内容は変化しない

  例に基づく単体テストは、実測で見つかった罠（トークンごとのかな化、空白区切りでの受け渡し）と誤読の実例（`葱`・`米`）を固定するために使う。
- **見直し条件**: 画面の組み立て自体の退行が実際に起きたとき。そのとき DOM を使うテスト環境の導入を検討する。

## Risks / Trade-offs

- [誤読が対応表に混入し、そのまま検索が当たらなくなる] → 誤読はかなとして妥当な形で出るため自動検出できない。対応表をコミットして差分レビューで拾う（D-15, D-16）。実測で判明している `葱→き`・`米→べい` は単体テストの例として固定する
- [読みの生成が macOS でしか動かない] → 生成物をコミットするのでビルド・CI・ブラウザは OS に依存しない（D-16）。読みを取得できない環境で生成を実行した場合は失敗させ、既存の対応表を変更しない（対応表が空になって訂正ごと失われるのが最悪の事故）。退路として `@sglkc/kuromoji` への切り替えを用意する（D-14）
- [入力側に漢字を打つと、かな表記のレシピが引けない] → 「鯖」で `サバ` は当たらない。かなで打てば当たるので、当面は打ち直しで回避する。頻発するなら対応表をブラウザにも配る（D-13 の見直し条件）
- [クエリパラメータの扱いを誤ると履歴が壊れる] → 打鍵ごとに履歴を積むとスマホの戻る操作が使えなくなる。D-23 の3ルールを守る。テストで検証しにくい領域なので、実機で確認する
- [`body` を検索対象に含めることによるノイズ] → `body` は Markdown ソースのまま（D-08）なので `## 手順` のような記法も検索に引っかかる。実際に使って邪魔になったら対象から外すか、記法を除去する
- [対応表が単調増加してレビューが形骸化する] → 生成側をまるごと書き直すことでゴミが消え、不要になった訂正は警告で知らせる（D-15）
- [スマホの実機でしか分からない挙動] → 日本語入力の変換イベントは端末と IME で挙動がばらつく。D-24 の「確定後にのみ検索する」は実機で確認したうえで調整する
- [`data/` の追加でディレクトリの意味が増える] → 「入力（`recipes/`）・公開物（`public/`）・処理（`scripts/`）・検証（`tests/`）・中間物（`data/`）」と役割を明示して混ざらないようにする

## Migration Plan

Phase 1 の成果物に対する破壊的変更は無い。検索インデックスにキーが増えるだけで、既存のキーの意味は変わらない。レシピの Markdown は無変更で通る。

導入は次の順になる。対応表が無い状態ではビルドが失敗するため、対応表の生成をビルドより先に行う必要がある。

1. 対応表を生成してコミットする（この時点でビルドが通るようになる）
2. ビルドが読みを焼き込むようにする
3. 検索画面と詳細表示を作る

ロールバックは、読みのキーと対応表を取り除けば Phase 1 の状態に戻る。ブラウザ側は読みのキーが空文字でも動くよう書いておくので、段階的に外すこともできる。

- 対応表の訂正がどれくらいの数に落ち着くか。数語で済むのか数十語になるのかで、掃除の警告の出し方を見直す余地がある
- スマホ実機での日本語入力の確定検出が、想定どおりに効くか（端末・IME による差の実測が必要）
