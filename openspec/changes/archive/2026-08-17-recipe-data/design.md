## Context

リポジトリには openspec の設定以外まだ何も無い。この change で、著者が書く Markdown レシピと、それを検索インデックス（JSON）に変換するビルドを作る。後続の検索 UI・公開はこの JSON の形だけを前提にするため、ここで決めたデータの形と生成の性質（fail fast・安定 ID・再現性）が以降の土台になる。

制約（config.yaml の常設制約より）: プロダクションコードは可能な限り標準 API のみ、第三者ライブラリは最小依存を選び D-番号で理由を明示／重い処理はビルド時に寄せる／frontmatter 解析に多機能ライブラリを持ち込まない／不備は fail fast／構造化データと層分離を壊さない／Node＋npm＋lockfile＋ESM／開発ツールは oxlint・oxfmt・vitest・fast-check。

## Goals / Non-Goals

**Goals:**
- 著者がレシピを1ファイル書けば、1コマンドで検証済みの検索インデックスが得られる
- 不備はビルド失敗として、どのファイルの何が悪いかが分かる
- ビルドの中核（frontmatter 解析・変換・検証）が単体テストとプロパティベーステストで守られている
- プロダクション依存は最小限（YAML 解析と Markdown 変換の2つ）に留め、ブラウザで動く第三者コードは増やさない
- lint・format・テストが npm scripts で揃い、以降の change でも同じ手順で品質を保てる

**Non-Goals:**
- 検索 UI・詳細表示・公開・CI（後続 change）
- レシピ Markdown 方言の網羅、独自記法の追加
- 検索用テキストの高度な正規化（記法除去・トークナイズ）

## Decisions

### D-01 データ化はビルド時に行い、ブラウザは JSON を読むだけにする
- **背景**: レシピは Markdown で管理したいが、ブラウザで Markdown と frontmatter を都度解析すると、第三者コードをブラウザに載せる量が増え、レシピの不備にも公開後まで気づけない。
- **検討した選択肢**:
  - ブラウザ側で Markdown を取得して解析・描画 → 解析ライブラリをブラウザに載せることになり「第三者コード最小」に反する。不備検出が実行時になる
  - サーバ／API で配信 → 静的サイト＋GitHub Pages・サーバ無しの前提に反する
  - **ビルド時（Node）で JSON に変換（採用）** → 検証・変換をすべて手元と CI で済ませられる。ブラウザは fetch＋検索のみ
- **帰結**: ビルド工程（Node・npm・lockfile）がリポジトリに常設される。JSON の形が「データ化」と「検索」の間の契約になる。
- **見直し条件**: レシピが数千件規模になり JSON 一括取得が重くなったら、分割や差分配信を検討する。

### D-02 frontmatter は自前の切り出し＋YAML パーサ js-yaml で解析する（多機能 frontmatter ライブラリは使わない）
- **背景**: 必要なのは「ファイル先頭の `---` ブロックを YAML として読む」だけ。一方、デファクトの多機能 frontmatter ライブラリは長期間リリースが止まり、古い YAML パーサや複数の凍結した小パッケージを引き連れる。ビルド時依存とはいえ、供給網は最小に保ちたい。他方、YAML 自体を自前で解析するのは「YAML と呼びながら YAML でない部分集合」を著者に強いることになり、エディタ補完とも食い違う。
- **検討した選択肢**:
  - 多機能 frontmatter ライブラリ → 実績はあるが凍結状態で依存が多い。TOML/JSON frontmatter などの機能は不要
  - 0依存の互換フォーク → 採用数が少なく精査の目が薄い。供給網としてはむしろ慎重に見るべき
  - YAML の部分集合を自前で解析 → 依存ゼロにでき攻撃面も小さいが、部分集合の境界を著者が覚える必要があり、拡張の誘惑が続く。保守が全部自分に乗る
  - YAML パーサ `yaml` → 依存ゼロ・現役だが実質1名メンテで、3.0 移行期。advisories は少ない
  - **YAML パーサ `js-yaml`（採用）** → 複数メンテナで旧系列にもバックポート、採用実績最大。推移的依存は CLI 用の `argparse` 1つのみで、ライブラリ利用では使われない。`load` は既定で安全なスキーマ。近年の advisories は信頼できない入力への計算量 DoS が中心で、自分のリポジトリのファイルを読む本用途では実害がない。ただし件数が多く `npm audit` が定期的に赤くなる運用コストは引き受ける
- **帰結**: スプリッタ（数十行の純関数）の正しさ——本文中の `---` を終端と誤認しない、CRLF・BOM、空 frontmatter、閉じ忘れ——は単体テストとプロパティベーステスト（往復性）で担保する。js-yaml は空入力で例外を投げるため呼び出し側で先に処理する。`048` のような値は YAML 1.2 では整数になるので、著者は引用符で囲む（README に例示）。
- **見直し条件**: js-yaml の保守が止まったとき（`yaml` へ切り替え。API 差は `load`→`parse` 程度）。frontmatter に YAML 以外の形式が必要になったとき。

### D-03 本文の Markdown→HTML 変換はビルド時に markdown-it で行い、生の HTML は通さない
- **背景**: 詳細表示で手順を整形して見せたい。変換をブラウザでやると第三者コードが増える（D-01）。本文は自分の書いた信頼できる内容だが、将来の共有や誤貼り付けに備え、生 HTML は無効化しておく方が安全。自前の部分集合レンダラも検討したが、著者の CommonMark の直感（入れ子リスト・強調・リンク）と実装の差が使い勝手を下げ、拡張の誘惑が続く。
- **検討した選択肢**:
  - Markdown の部分集合を自前実装 → 依存ゼロだが、著者が対応記法を意識し続ける必要があり、エスケープの正しさも自分で担保する。将来外部レシピを扱うなら書き直しになる
  - `marked` → 依存ゼロ・現役だが、生 HTML の無効化に組み込みオプションが無く、レンダラ上書きで自前エスケープを書くことになる（信頼境界を自分のコードで支える）
  - unified／micromark 系の変換パイプライン → 拡張性は高いが依存木が大きく、今回の用途には過剰
  - **`markdown-it`（採用）** → CommonMark 準拠。生 HTML の無効化が設定1つ（`html: false`）で、信頼境界を自分のコードでなく設定で保証できる。推移的依存 6 つはすべて同一メンテナ群のもの
  - ブラウザ側で変換 → D-01 で不採用
- **帰結**: `body_html` は生 HTML 無効・単一改行を `<br>` にする設定で生成する（リンク自動化は使わない。必要なら Markdown のリンク記法で書く）。ブラウザ側は `body_html` をそのまま挿入してよい（信頼境界はビルド時に置く）。「任意の本文を入れても `body_html` に生の `<script` が現れない」をプロパティベーステストで契約として固定し、設定の退行を検知する。
- **見直し条件**: レシピを外部から受け取るようになったら、生成側の無効化に加えて表示側でもサニタイズを検討する。markdown-it の保守が止まったとき。

### D-04 不備は全ファイル分を集めてからまとめて失敗させる
- **背景**: fail fast は決まっているが、「最初の1件で即終了」か「全件検証して一覧で失敗」かは別の判断。レシピを数件まとめて追加したとき、1回のビルドで全部の不備が分かる方が直しやすい。
- **検討した選択肢**:
  - 最初の不備で即終了 → 実装は最も単純。ただし直して再実行、を不備の数だけ繰り返す
  - **全件検証して不備一覧を出し、1件でもあれば失敗（採用）** → 一度で全部直せる。実装は誤りをリストに積むだけで済む
  - 不備のあるレシピをスキップして続行 → 「気づけない」を招くので不採用
- **帰結**: ビルドは検証フェーズと出力フェーズを分け、検証で1件でも失敗があれば出力しない（不完全なインデックスで上書きしない）。
- **見直し条件**: なし（規模が変わっても成立する）。

### D-05 レシピの ID はファイル名（著者が手動で付けるローマ字スラッグ）とする
- **背景**: 検索 UI が URL でレシピを指し示す（後続 change）ため、安定した ID が要る。
- **検討した選択肢**:
  - 料理名から自動生成 → 日本語のローマ字化・重複回避が必要でライブラリが増える。料理名を直すと ID が変わる
  - frontmatter に `id` 項目 → 安定はするが、ファイル名との二重管理と重複チェックが要る
  - 連番 → 追加・削除で意味が崩れる。番号の割り当てを著者が管理することになる
  - **ファイル名＝ID（採用）** → 一意性はファイルシステムが保証。料理名を変えても ID は不変。ファイル名変更は明示的な ID 付け替え
- **帰結**: 著者はファイル名を URL に載る前提で付ける（ローマ字・小文字・ハイフン）。ビルドは形式を強制しないが README で規約として示す。
- **見直し条件**: レシピを外部から取り込むようになり、ファイル名を著者が管理できなくなったとき。

### D-06 任意項目は「空文字」に正規化する
- **背景**: 下流（検索・表示）が項目の有無を毎回 `undefined` / `null` / 空文字で分岐するのは煩雑で、バグの温床になる。
- **検討した選択肢**:
  - 無い項目はキーごと省略 → JSON が小さくなるが、下流に存在チェックを強いる
  - `null` → 「無い」を表せるが、空文字との二値管理になる
  - **空文字に統一（採用）** → 「値が無い＝空」の1通り。表示は truthy 判定だけで済む
- **帰結**: `ingredients` は配列のまま（空要素・前後空白を除去）。数値に見える `menu_no` も文字列として保つ。
- **見直し条件**: 「未記入」と「意図的に空」を区別する必要が生じたとき。

### D-07 並びは料理名の日本語ロケール昇順、出力は決定的にする
- **背景**: 入力前の初期表示で全件が並ぶ想定（後続 change）。ファイルシステムの列挙順は環境依存なので、そのままでは再現性が無い。
- **検討した選択肢**:
  - ファイル名順 → 決定的だが、表示上の意味が薄い（ローマ字順）
  - 更新日順 → Git のチェックアウトで mtime が変わり再現性が無い
  - **料理名の日本語ロケール照合順（採用）** → 表示上自然で、同じ入力から同じ出力になる
- **帰結**: 照合は実行環境の ICU に依存するが、Node は既定で完全な ICU を同梱するため手元と CI で一致する。
- **見直し条件**: 検索 UI 側で並び替え機能を持つようになったら、ビルド側の並びは「安定していれば何でもよい」に緩める。

### D-08 検索用 `body` は Markdown ソースをそのまま持つ
- **背景**: 検索対象に本文を含めたいが、記法を除去したプレーンテキストを作るには変換器のトークンからテキストを再構成する処理が要る。
- **検討した選択肢**:
  - 記法を除去したプレーンテキスト → 検索ノイズは減るが処理が増え、除去の仕様（リンク・強調の扱い）を決める必要がある
  - **Markdown ソースをそのまま（採用）** → 実装ゼロ。`## 手順` などの記法が検索に引っかかりうるが、あいまい検索なら実害は小さい
- **帰結**: `body` と `body_html` は同じ本文の2表現であり、片方だけ更新されることはない。
- **見直し条件**: 記法由来の検索ノイズが体感で問題になったら、変換器のトークンからプレーン化する。

### D-09 ビルド生成物はコミットせず、手元と CI で再生成する
- **背景**: 検索インデックスは入力から決定的に生成できる（D-07）。コミットすると PR の差分に生成物が混ざり、レビューと競合の原因になる。
- **検討した選択肢**:
  - 生成物をコミット → 公開側でビルド不要になるが、生成し忘れ・手編集・差分ノイズの温床
  - **コミットしない・無視対象にする（採用）** → 「入力＝Markdown、出力＝ビルド」の一方向が保たれる。公開時は CI がビルドする（後続 change）
- **帰結**: 公開ディレクトリには手書きの静的ファイルと生成物が同居するので、生成物のパスだけを無視対象にする。
- **見直し条件**: 公開経路でビルドが実行できなくなったとき。

### D-10 テストは vitest＋fast-check で、単体テスト・プロパティベーステスト・フィクスチャの3層で書く
- **背景**: 守りたいのは frontmatter スプリッタのエッジケース、ビルド全体の fail fast・出力の形、そしてライブラリ設定（生 HTML 無効）の退行。例に基づく単体テストだけでは「本文中の `---`」のような境界を網羅しきれないので、性質で検証したい。
- **検討した選択肢**:
  - Node 標準ランナー＋fast-check → fast-check はランナー非依存なので成立し、依存も少ない。ただしウォッチ・カバレッジしきい値は別途用意することになる
  - 外部フレームワークのみ（プロパティテスト無し） → 境界の網羅を例の列挙に頼ることになる
  - テストなし → D-02／D-03 の「自分で担保する」が空手形になる
  - **vitest＋fast-check（採用）** → ウォッチ・カバレッジが揃い、他リポジトリと運用が統一できる。開発時依存なのでプロダクション依存の方針とは衝突しない
- **帰結**: プロパティで固定する性質は次の3つ。(a) スプリッタの往復性：任意の frontmatter 内容と任意の本文（`---` 行を含みうる）を結合→分割すると元に戻る。(b) ビルド正規化の不変条件：任意の入力から得た出力は必ず8キー・任意項目は空文字・料理名順・2回ビルドで同一。(c) レンダラ契約：任意の本文に対して `body_html` に生の `<script` が現れない。スプリッタは純関数として切り出して直接テストし、ビルドは「入力ディレクトリ・出力先を引数で差し替えられる関数」にして、正常系・各不備のフィクスチャで検証する。
- **見直し条件**: プロパティテストの実行時間が開発の妨げになったら、反復回数を CI と手元で分ける。

### D-11 ディレクトリ配置とコマンド
- **背景**: 著者の編集場所・公開物・ビルド処理・テストの置き場を最初に固定しないと、後続 change ごとにブレる。
- **検討した選択肢**:
  - すべてルート直下 → 小さいうちは楽だが、公開ディレクトリの境界が曖昧になる
  - テストをプロダクションと同じディレクトリに並置 → 見つけやすいが、lint／format／カバレッジの対象指定が煩雑になる
  - **`recipes/`（著者編集）／`public/`（公開物。生成物もここ）／`scripts/`（ビルド。プロダクションのみ）／`tests/`（テスト本体と `fixtures/`）（採用）** → 「入力・出力・処理・検証」が1階層で見て分かり、ツールの対象指定も単純
- **帰結**: npm scripts は `build`（検証＋生成）／`test`・`test:watch`・`test:coverage`／`lint`・`lint:fix`／`format`・`format:check`。Node 版は mise に従い、`package.json` の `engines` にも記して不一致に気づけるようにする。
- **見直し条件**: 公開物のルートを変える必要が出たとき（GitHub Pages のパス設定など。後続 change で確認する）。

### D-12 lint／format は oxlint／oxfmt、依存の取り込みは公開直後を避ける
- **背景**: プロダクションコードは標準 API 中心のプレーン JS なので、型検査よりも「未使用・未定義・明白な誤り」を機械的に止め、整形の揺れを無くすことが効く。また依存追加時に公開直後の版を掴むと、乗っ取り版を取り込むリスクがある。
- **検討した選択肢**:
  - ESLint＋Prettier → 実績最大だがプラグイン依存が多く、設定も重い
  - Biome → 一体型で速いが、他リポジトリとの運用統一を優先したい
  - lint／format 無し → 一人開発でも整形の揺れと初歩的なミスは積もる
  - **oxlint（`correctness` を error）＋oxfmt（採用）** → 依存が軽く高速。フィクスチャと生成物は対象外にする
  - `.npmrc` `min-release-age=7` を置く（採用）→ 依存の解決時にだけ効き、`npm ci` には影響しない。`npm audit fix` が新しすぎる修正版を掴めない場合は `min-release-age-exclude` で一時的に除外する
- **帰結**: `npm run lint` と `npm run format:check` がタスク完了の条件になる（config.yaml の apply guidance）。TypeScript／型検査は今回入れない（プレーン JS をビルド無しで書く前提を優先）。
- **見直し条件**: JSDoc だけでは型の食い違いを追えなくなったら、`tsc --noEmit --checkJs` の導入を別 change で検討する。

## Risks / Trade-offs

- [自前スプリッタの見落とし（本文中 `---`、CRLF、BOM、閉じ忘れ、空 frontmatter）] → 例のフィクスチャに加え、往復性のプロパティテストで固定する（D-10）
- [js-yaml・markdown-it のサプライチェーン（CI 上で第三者コードが動く）] → 版は lockfile で厳密固定し、`npm ci` で integrity 検証。`min-release-age` で公開直後の版を避ける（D-12）。推移的依存はどちらも同一メンテナ群のものに限られる
- [js-yaml の advisories が頻繁で `npm audit` が赤くなる] → 内容は信頼できない入力への DoS が中心で本用途では実害なし。修正版が `min-release-age` に引っかかる間は `min-release-age-exclude` で一時対応、または待つ
- [レンダラ設定の退行（`html: true` に戻す等）] → 「任意の本文で `body_html` に生の `<script` が現れない」を契約テストとして常設（D-03, D-10）
- [ロケール照合の環境差] → Node 同梱の ICU に依存。CI と手元の Node 版を mise／engines で揃える（D-11）
- [`body_html` を信頼して挿入する設計] → 信頼境界をビルド時に置く（生 HTML 無効）。外部レシピを受け入れるなら D-03 の見直し条件に従う
- [`menu_no` を引用符なしで書くと数値化され先頭ゼロが落ちる] → README の記述例で引用符を示す。ビルドは文字列化はするがゼロ復元はしない（著者の責任範囲として明示）
- [開発ツール（oxlint／oxfmt／vitest）の版更新が速い] → lockfile と `min-release-age` で制御し、更新は意図的に行う

## Migration Plan

新規リポジトリのため移行対象なし。ロールバックは change の取り消し（ファイル削除）で足りる。

## Open Questions

- README に載せる「現在の機種名」の実値（利用者が記入する。実装時はプレースホルダを置く）
- サンプルレシピを何件・どんな内容で同梱するか（フィクスチャとは別に、実運用の初期データとして2〜3件を想定）
- カバレッジのしきい値を設けるか（設けるなら対象はスプリッタとビルド関数に限る）。実装後に実測を見て決める
