## Why

ホットクックの自作レシピを「今日何を作ろう」と思ったときに料理名や具材で探せるサイトを作りたい。その土台として、著者が Markdown でレシピを書く形式と、それを検索用の構造化データに変換するビルドを、まず定める必要がある。検索 UI も公開も、この構造化データがあって初めて成立するため、最初の change として切り出す。

## What Changes

- レシピの著者向け記述形式（1レシピ＝1 Markdown ファイル、frontmatter＋本文）を定義する
- 必須項目・任意項目と、その意味（料理名・材料・自動調理キー・自動メニュー番号・手動設定）を定める。機種は記録しない
- レシピ群を検索用の構造化データ（JSON）に変換するビルドを用意する。安定した ID を持ち、料理名順に並ぶ
- レシピの不備（必須項目欠落・YAML 破損など）はビルドを失敗させ、ファイル名と理由を示す（fail fast）
- ビルドの単体テストとプロパティベーステストを用意し、lint・format と合わせて手元の npm scripts で回るようにする
- 開発の前提となるリポジトリ骨格（パッケージ管理・Node 版の固定・無視ファイル・開発ツール設定）を整える

## Non-goals

- 検索 UI・レシピ詳細表示（次の change）
- GitHub Pages への公開・CI（その次の change）
- レシピ本文の Markdown 方言の網羅的な仕様化（CommonMark に準拠して変換できれば足りる。独自記法は追加しない）
- 複数機種の番号管理、レシピの共有・配布
- 意味検索・AI 連携（構造化データを壊さないことだけ守る）

## Capabilities

### New Capabilities
- `recipe-authoring`: 著者が書く Markdown レシピの形式。frontmatter の項目・必須／任意・値の形・機種を記録しないこと・不備の扱い
- `search-index`: レシピ群から生成される検索用構造化データの内容と保証（安定 ID・並び・本文のプレーン／HTML 両表現・生成失敗の条件）

### Modified Capabilities
（なし。既存 spec はまだ存在しない）

## Impact

- 新規: `recipes/`（レシピ置き場）、ビルドスクリプト、テスト（単体・プロパティ・フィクスチャ）、`package.json` / lockfile、`.gitignore`、開発ツールの設定ファイル
- 生成物: 検索用 JSON（公開ディレクトリ配下。コミット可否は design で決める）
- 依存: プロダクション（ビルド時）依存は YAML 解析と Markdown→HTML 変換の2つに限り、最小依存のものを選ぶ。開発ツール（lint・format・テストランナー・プロパティベーステスト）は devDependencies。ブラウザで動く第三者コードはこの change では増えない
- 後続 change への契約: 検索 UI は本 change が定める JSON の形だけを前提にする
