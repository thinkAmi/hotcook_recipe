# add-recipe-skill 設計

## Context

レシピは「一度作って、これで行けると感じたもの」を調理直後に振り返って記録する。記録の頻度が低いため frontmatter の形式を毎回思い出すのは負担で、聞き書きでレシピファイルを生成し、その場でビルド検証まで済ませる仕組みを作る（proposal 参照）。

探索の中で、材料の並びには「ホットクックに投入する順」という暗黙の意味があることが分かった。これは spec（recipe-authoring）の要件に昇格する。生成の仕組みは、この規約を壊さないことを最優先の制約とする。

## Goals / Non-Goals

**Goals:**

- 著者の語りから、レシピ形式に準拠した Markdown ファイルを対話で生成する
- 生成後にビルドを実行し、fail fast の検証と読みの警告確認までをその場で行う
- 材料の投入順を保持する（勝手に並べ替えない）

**Non-Goals:**

- proposal の Non-goals に同じ（コミット自動化・メニュー番号対応表・ポータブルプロンプト・読みの自動推測・既存レシピの一括変換はしない）

## Decisions

### D-37: 実現形態は Claude Code のプロジェクトスキルとする

- **背景**: 「プロンプトからレシピファイルを生成する仕組み」の置き場所と形を決める必要がある。
- **検討した選択肢**:
  - **プロジェクトスキル（採用）**: リポジトリ内に置き、スラッシュコマンドで起動する。
  - **ポータブルなプロンプト文書**: docs 等に置き、スマホの AI チャットに貼って使う。生成された文面を後で手動コミットする必要があり、ビルド検証まで一気通貫できない。記録のきっかけは「作った直後の振り返り」であり、外出先で書く動機が薄いため不採用。
  - **対話式の Node CLI**: 標準入力で項目を訊くスクリプト。自由な語りから項目を抽出する柔軟さがなく、質問票と同じ硬さになる。プロダクションコードでもないのに保守対象のコードが増えるため不採用。
- **帰結**: スキルはファイル生成とビルド実行までを担い、リポジトリの慣行（既存の `.claude/skills/`）に沿って配置する。
- **見直し条件**: 外出先で記録したい場面が実際に繰り返し発生したら、ポータブル版を「足し算」で検討する。

### D-38: 対話は「聞き書き」型とし、確認は最後の全文プレビュー1回に集約する

- **背景**: 著者は自由形式で語る。一括で全部語ることも、断片だけのこともある。手間を掛けたくないという動機と、聞き取りの正確さを両立する対話設計が要る。
- **検討した選択肢**:
  - **聞き書き型（採用）**: まず語りから埋まる項目をすべて抽出し、不足分だけを質問する。「語られたことは訊き直さない」を原則とし、最後にファイル名＋全文プレビューを1回提示して承認を得る。
  - **固定質問票型**: 料理名→材料→…と毎回同じ順で訊く。全部語った後に同じことを訊かれる徒労があり、記録のたびの手間が増えるため不採用。
  - **項目ごとの逐次確認型**: 項目を埋めるたびに確認を挟む。確認回数が最も多く、コミット前にも著者確認（既存の運用）が控えているため過剰。不採用。
- **帰結**: 全部語られたら質問ゼロでプレビュー直行できる。聞き取り誤り・言っていない材料の混入は、最後のプレビューで著者が捕捉する。
- **見直し条件**: プレビュー1回では誤りを見落とすことが実際に起きたら、材料だけ先に確認する等の中間確認を足す。

### D-39: 投入順の確認は、順序が曖昧に語られたときだけ行う

- **背景**: 材料の並びは投入順であり（spec に昇格）、生成側が区分順などへ「善意で」並べ替えると、見た目は正しいまま静かに規約が壊れる。一方、毎回「この順でいいですか」と訊くのは煩わしい。
- **検討した選択肢**:
  - **トリガー式（採用）**: 語られた順をそのまま投入順として使う。「材料は豚バラと大根、味付けはめんつゆ」のように区分でまとめて語られた場合など、順序が投入順と読めないときだけ確認する。
  - **毎回確認**: 確実だが、順に語ってくれた大半のケースで徒労になり、聞き書きの軽さを損なう。不採用。
  - **確認なし（常に語られた順を採用）**: 区分で語られたときに誤った順で記録され、プレビューでも著者が見落としやすい。不採用。
- **帰結**: スキルのプロンプトに「材料を並べ替えない。順序が投入順と読めないときだけ確認する」を焼き込む。「曖昧」の判定基準はあえて詰めない。
- **見直し条件**: 運用して「訊いてほしいのに訊かれない」「毎回訊かれて煩わしい」のどちらかが気になったら、判定基準を具体化する。

### D-40: スラッグは既存の流儀（ヘボン式・外来語は英語綴り）で候補を提示し、著者が承認する

- **背景**: ファイル名（＝レシピ ID）はローマ字スラッグで著者が付ける、が既存要件。既存3件を観察すると `saba-misoni`・`mushi-yasai-salad` のように、基本はヘボン式ローマ字、外来語は元の英語綴り（sarada ではなく salad）という癖がある。
- **検討した選択肢**:
  - **既存の流儀で候補提示→承認（採用）**: スキルが流儀に沿った候補を1つ出し、著者が承認または修正する。「著者が付ける」の精神を保つ。
  - **厳密な命名規則を定義する**: 表記規則を spec 化する。ファイル名を参照して何かをする機能は無く、多少の表記揺れは許容できるため過剰。不採用。
  - **スキルが自動確定する**: 承認を省けるが、「ファイル名は著者が付ける」という既存要件と衝突する。不採用。
- **帰結**: 同名ファイルが既にある場合は衝突を検知し、別案を提示する。表記揺れは許容する。
- **見直し条件**: ファイル名を機械的に参照する機能（URL 設計等）が将来生まれたら、命名規則の厳密化を検討する。

### D-41: ビルド失敗はスキルが直し、読みの警告は提示して口述の訂正だけを書き取る

- **背景**: 生成後のビルドで起きることは2種類ある。fail fast の失敗（必須欠落・YAML 破損）と、読みの警告（新しい食材の読みが取れない）。それぞれ責任の所在が違う。
- **検討した選択肢**:
  - **失敗と警告で振る舞いを分ける（採用)**: ビルド失敗は生成物の不備でありスキルの責任なので、スキルが直して再ビルドする。読みの警告は著者に提示し、著者がその場で読みを口にしたら `yomi.overrides.json` への書き取りまで行う。著者が何も言わなければ何もしない。
  - **すべて著者に返す**: ビルド失敗の修正まで著者にやらせるのは、形式の負担を消すという目的に反する。不採用。
  - **読みもスキルが推測して自動で埋める**: 誤読が訂正として焼き込まれると、再生成でも上書きされず静かに検索が壊れる。読みの正誤は著者にしか分からない。不採用。
- **帰結**: 「訂正の自動化はしない」（proposal の Non-goals）の線引きは「スキルが読みを推測して埋めることはしない」であり、著者が口にした読みを書き取るのは聞き書きの範囲内とする。
- **見直し条件**: 書き取った訂正に誤記が混ざる事故が起きたら、訂正もプレビュー承認の対象に含める。

### D-42: 自動化の終点はビルド検証までとし、コミットは既存の流れに委ねる

- **背景**: 生成→検証→コミットまで一気に進めることも技術的には可能で、どこで止めるかを決める必要がある。
- **検討した選択肢**:
  - **ビルド検証まで（採用）**: fail fast の恩恵をその場で受け、レシピとして成立していることを確認して止める。コミットは著者が内容を確認してから既存のコミット規約の流れで行う。
  - **コミットまで自動化**: 手数は最少だが、記録内容を確認せずに履歴へ入る。基本はそのまま進められる想定でも「念のため確認したい」という運用方針に反する。不採用。
  - **ファイル生成のみ（検証なし）**: 形式の誤りに次のビルドまで気づけず、fail fast をその場で活かせない。スキルを作る動機の半分が消える。不採用。
- **帰結**: スキルの完了報告は「生成したファイル・ビルド結果・読みの警告の有無」まで。コミットはしない。
- **見直し条件**: 運用が安定し、確認が形骸化していると感じたらコミットまでの自動化を再検討する。

## Risks / Trade-offs

- [生成側が材料を区分順などへ並べ替えてしまう] → プロンプトに並べ替え禁止を明記し（D-39）、最後の全文プレビューで著者が順序を確認する（D-38）
- [語られていない材料・分量を補完してしまう（幻覚）] → 「語られたことだけを書く。推測で埋めない」をプロンプトに焼き込み、プレビューで捕捉する
- [スキルを使わず手書きした場合は規約を守る仕組みがない] → 投入順を spec に昇格して規約自体は残す。ただし順序の正しさは機械検証できず著者責任のまま（ビルドが検証するのは順序の保持のみ）
- [「曖昧なとき」の判定が安定しない] → 許容して運用で観察する。D-39 の見直し条件で拾う
