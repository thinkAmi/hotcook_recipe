## Why

レシピを Markdown で書き、検索できる画面まで揃った。しかし公開していないため、実際に「今日何を作ろう」と思ったときに手元の開発環境を立ち上げないと使えない。台所でスマホから引けて初めて道具になるので、公開経路を用意する。

あわせて、いま検証が手元にしか無い。手元の Node が固定した版とずれることが実際に起きており、気づかないまま壊れたものを公開する経路を作りたくない。公開と同時に、変更を取り込む前の検証も自動で回るようにする。

## What Changes

- 検索サイトを GitHub Pages で公開する。`main` への push と、必要なときの手動実行で公開される
- 変更を取り込む前（プルリクエスト）に、ビルド・テスト・lint・整形の検証を自動で回す。デプロイはしない
- 検証が失敗したら公開しない。公開済みのサイトは直前の成功版のまま残る
- 公開経路で使う Node の版を、リポジトリが固定している版に合わせる
- 公開経路では読みの対応表を再生成しない（生成が macOS を要するため）。コミット済みの対応表をそのまま使う
- README に公開 URL と、公開の仕組みを1節書く

## Non-goals

- ブランチ保護・必須ステータスチェックの設定（新メニューはプルリクエスト、軽微な修正は直 push と選べる自由を残す）
- 独自ドメイン、アクセス解析、サイトマップ、OGP などの公開まわりの装飾
- プレビュー環境（プルリクエストごとの一時 URL）
- リリースタグ・バージョニング。レシピは継続的に増えるもので、版を切る意味が薄い
- 依存の自動更新（Dependabot / Renovate）
- 公開経路での読みの対応表の生成。macOS 依存を CI に持ち込まない
- レシピの記述形式・検索の振る舞いの変更

## Capabilities

### New Capabilities
- `site-delivery`: 検索サイトが公開される経路の振る舞い。何を公開するか、いつ公開されるか、検証が通らないときに何が起きるか、公開されたサイトが満たすこと

### Modified Capabilities
（なし。既存 5 capability の要件は変わらない）

## Impact

- 新規: 公開と検証のワークフロー定義、README の公開に関する記述
- 前提: GitHub リポジトリの Pages 設定を「GitHub Actions」に切り替える必要がある（リポジトリ設定の変更なので、実装とは別に人が行う）
- 依存: 実行環境の Node は `.node-version` に従う。パッケージは lockfile どおりに入れる
- 既存への影響: `recipes/` の書き方、検索インデックスの形、検索・詳細の振る舞いは変わらない
