## Context

レシピの記述形式・検索インデックスの生成（Phase 1）と、検索画面・詳細・読み（Phase 2）は実装済みで、手元では動く。残っているのは配信だけ。

配信の設計を縛る事実が3つある。

1. **読みの取得は macOS を要する**。対応表はコミット済みで、ビルド・ブラウザは OS に依存しない（archive 済み change `recipe-search-site` の D-14・D-16）。公開経路で対応表を作り直すと、Linux 実行環境では必ず失敗する
2. **手元の Node が固定した版とずれることが実際に起きた**。CLAUDE.md にその回避手順を残してある。公開経路では実行環境を固定できるので、ここが「ずれない場所」になる
3. **検索インデックスはコミットしていない**。配信するには公開経路でビルドする必要がある

決定の通し番号は、archive 済みの change から続けて D-29 から振る。

## Goals / Non-Goals

**Goals:**
- レシピを追記して取り込めば、手を動かさずに公開サイトが更新される
- 壊れたものが公開されない。失敗しても公開中のサイトは無事
- 検証が「手元でやっていること」と同じで、CI 用の別物にならない
- 実行環境の Node が、リポジトリの版の指定に自動で追従する

**Non-Goals:**
- ブランチ保護・必須チェック。関門は作らない
- プレビュー環境、独自ドメイン、リリースタグ、依存の自動更新
- 公開経路での読みの生成

## Decisions

### D-29 公開は GitHub Actions から行い、ブランチを経由しない
- **背景**: GitHub Pages には「ブランチの内容を配信する」方式と「ワークフローが作った成果物を配信する」方式がある。検索インデックスはコミットしていないので、前者を採るには生成物をコミットするか、配信用ブランチを別に持つ必要がある。
- **検討した選択肢**:
  - 配信用ブランチ（`gh-pages` 等）に生成物を push → 生成物がリポジトリの履歴に入り、「入力＝Markdown、出力＝ビルド」の一方向（D-09）が崩れる。差分もノイズになる
  - 検索インデックスをコミットして既定のブランチから配信 → 生成し忘れ・手編集の余地が生まれる。D-09 の判断を覆すことになる
  - **ワークフローが作った成果物を配信（採用）** → リポジトリに生成物を残さずに公開できる。ビルドは公開のたびに走るので、配信物と入力が必ず一致する
- **帰結**: リポジトリ設定の Pages の Source を「GitHub Actions」にする必要がある。これはワークフローからは行わず、人が一度だけ設定する（設定変更を自動化すると、権限の要求範囲が広がるわりに一度きりの作業）。
- **見直し条件**: 生成物をコミットする方針に変えたとき（D-09・D-16 の線引きを変えることになる）。

### D-30 検証と公開でワークフローを分け、公開側でも同じ検証を通す
- **背景**: 検証は「取り込む前に気づくため」と「壊れたものを公開しないため」の2つの目的で要る。引き金も、対象とするブランチも異なる。
- **検討した選択肢**:
  - ワークフロー1本で条件分岐 → 引き金と権限（公開には書き込み権限が要る）が混ざり、読みにくい。検証だけしたい場面でも公開用の権限を要求することになる
  - 検証は提案時のみ、公開側では検証しない → 既定のブランチへ直接 push したときに素通りする。「軽微な修正は直 push」を許す運用（Non-goals のブランチ保護なし）と噛み合わない
  - **2本に分け、公開側でも同じ検証を先に通す（採用）** → 権限を最小に分離でき、どちらの経路からでも壊れたものは公開されない。検証が二重に走るのは意図的な冗長性
- **帰結**: 検証の中身は1か所に書けないので、2つのワークフローに同じ手順が並ぶ。手順が増えたときに片方だけ直す取りこぼしが起こりうる。
- **見直し条件**: 検証の手順が増えて重複が保守の負担になったら、再利用可能ワークフローに切り出す。

### D-31 検証は手元と同じ4つを回す
- **背景**: 「ビルド検証だけ」でも公開の安全は守れる（レシピの不備はビルドが弾く）。ただしテストと静的検査を回さないなら、それらは手元でしか実行されない。手元の Node が固定した版とずれる事象が実際に起きている以上、「手元では通った」は根拠として弱い。
- **検討した選択肢**:
  - ビルドだけ → 速い。レシピの不備は防げるが、実装の退行は防げない
  - ビルドとテストだけ → 静的検査と整形の揺れが混ざり込む
  - **ビルド・テスト・静的検査・整形の確認の4つ（採用）** → 手元で完了条件にしているものと同じ。CI 専用の検証を作らないので、片方だけ通る状態が生まれない
- **帰結**: 検証にかかる時間は伸びるが、いずれも数秒〜十数秒の規模で問題にならない。手元の完了条件を増やしたら、公開経路にも同じものを足す。
- **見直し条件**: 検証時間が開発の妨げになったら、提案時と公開時で回すものを変える。

### D-32 実行環境の Node は版の指定ファイルから読む
- **背景**: 版を固定する指定はリポジトリにある。公開経路にも版を書くと二重管理になり、片方だけ更新したときに「手元では通ったのに公開で落ちる」を作る。これはこのリポジトリが避けると決めている状態そのもの。
- **検討した選択肢**:
  - ワークフローに版を直接書く → 一目で分かるが二重管理。更新のたびに2か所を直すことになる
  - 版の範囲指定（最新の LTS など）を使う → 更新は不要だが、ある日黙って別のメジャー版に移る
  - **版の指定ファイルを読ませる（採用）** → 単一の真実源が保たれる。版を上げるときの変更は1ファイルで済む
- **帰結**: 版を上げると、次の検証から新しい版で走る。手元と公開経路が同時に切り替わる。
- **見直し条件**: なし（このリポジトリの版管理の方針そのもの）。

### D-33 パッケージは lockfile どおりに入れ、公開経路では対応表を作り直さない
- **背景**: 公開経路が入力を勝手に変えると、配信物が手元での確認と一致しなくなる。読みの取得は macOS を要するので、Linux で実行すれば失敗する。
- **検討した選択肢**:
  - 最新の依存を解決して入れる → 供給網の観点で危うく、lockfile を持つ意味が消える
  - 公開経路で対応表も作り直す → 実行環境を macOS にすれば可能だが、公開のたびに読みが揺れうるうえ、誤読を人が見る機会（差分レビュー）が失われる
  - **lockfile どおりに入れ、対応表はコミット済みのものを使う（採用）** → 配信物が手元での確認と一致する。macOS 依存は生成の場面だけに閉じたままになる
- **帰結**: 読みを更新するのは著者の手元での明示的な操作だけ。公開経路は対応表を読むだけで、書かない。
- **見直し条件**: 読みがどの環境でも再生成できるようになったとき（`recipe-search-site` の D-14 の退路に切り替えたとき）。

### D-34 使う Action は commit のハッシュで固定する
- **背景**: Action をタグで参照すると、同じタグが別の中身に付け替えられたときに、公開の権限を持つ実行環境で意図しないコードが動く。このリポジトリは供給網について「版を明示して検証可能にする」立場を取っている。
- **検討した選択肢**:
  - タグ参照 → 読みやすく更新も楽だが、付け替えを検知できない
  - **commit のハッシュで固定し、横に版をコメントで書く（採用）** → 付け替えの影響を受けない。人が読むときは版が分かる
  - ハッシュ固定を検証する仕組みも同時に入れる → 固定漏れを機械的に防げるが、ワークフローがもう1本増える。今回は入れず、必要になってから足す
- **帰結**: Action を更新するときは、ハッシュとコメントの版を両方直す。更新の手間は増えるが、頻度は低い。
- **見直し条件**: Action の数が増えて手作業での固定が漏れ始めたら、固定を検証する仕組みを足す。リポジトリ設定側で固定を強制できるなら、そちらでもよい。

### D-35 公開に与える権限は必要な3つだけにする
- **背景**: 既定では、ワークフローに与えられる権限が必要以上に広いことがある。公開は書き込みを伴う操作なので、範囲を明示して絞りたい。
- **検討した選択肢**:
  - 既定のまま → 設定は減るが、何が許されているかがワークフローを読んでも分からない
  - **読み取り・Pages への書き込み・身元証明の3つだけを明示（採用）** → 公開に必要な最小。検証だけのワークフローは読み取りのみにする
- **帰結**: 将来この経路から別の操作（コメント投稿など）をしたくなったら、そのつど権限を足すことになる。足す理由がその場で言語化される。
- **見直し条件**: なし。

### D-36 公開は同時に1つだけ走らせ、追い越しを許さない
- **背景**: 短い間隔で2回取り込むと公開が2つ並走し、古いほうが後に完了して内容が巻き戻ることがある。
- **検討した選択肢**:
  - 何もしない → 巻き戻りが起こりうる。原因が分かりにくい
  - **同時実行を1つに制限し、走っている古いものは打ち切る（採用）** → 最後に取り込まれた内容が必ず最後に公開される
- **帰結**: 連続して取り込んだとき、途中の版は公開されずに飛ばされる。公開したいのは常に最新なので問題にならない。
- **見直し条件**: なし。

## Risks / Trade-offs

- [検証の手順が2つのワークフローに重複する] → 手元の完了条件を増やしたときに片方だけ直す取りこぼしが起こりうる。重複が負担になったら再利用可能ワークフローへ（D-30）
- [Pages の Source 設定を人が行う必要がある] → 設定しないと公開のワークフローが失敗する。実装のタスクに「人が行う設定」として明記し、README にも残す
- [公開経路の実行環境で読みを生成できない] → 生成は行わない設計にしてある（D-33）。将来 macOS 実行環境を使いたくなっても、対応表の形は変わらないので非破壊で切り替えられる
- [Action のハッシュ固定は更新の手間が増える] → 数が少ないうちは手作業で足りる。増えたら検証の仕組みを足す（D-34）
- [公開サイトは誰でも見られる] → レシピは自分用の記録であり、公開して困る内容ではない。個人を特定する情報を書かない運用は続ける
- [検索インデックスを公開のたびに作り直す] → 入力と配信物が必ず一致する利点のほうが大きい。レシピが数千件になったら生成時間を見直す

## Migration Plan

新規の経路なので移行対象なし。うまく動かない場合は、公開のワークフローを止めれば公開中のサイトはそのまま残る。ロールバックは、直したい内容を取り込み直して再公開する。
